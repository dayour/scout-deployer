2. Architecture - why it is shaped this way

Public client, no secret

A desktop app cannot keep a secret confidential. {{SCOUT_APP_NAME}} uses MSAL public-client flows (interactive + device code + silent refresh). The registration sets isFallbackPublicClient = true ("Allow public client flows") and ships zero credentials.

Deep-link redirect, not localhost

Instead of an http(s)://localhost loopback, the app registers the custom scheme ms-clawpilot://. Azure AD redirects to ms-clawpilot://auth/callback; Electron intercepts it via open-url (macOS) or second-instance (Windows/Linux). This satisfies SPACE/compliance (no localhost web reply URL).

macOS broker URIs

On macOS the MSAL native broker uses msauth.<bundleId>://auth. The signed build uses msauth.com.microsoft.clawpilot://auth; unsigned/dev builds fall back to the shared msauth.com.msauth.unsignedapp://auth.

Delegated Graph scopes

Scopes are derived from BASE_SCOPES + FEATURE_SCOPES in electron/auth/msal-provider.ts: mail, calendar, files, Teams chat, and people, on top of the OIDC base. All delegated (acting as the signed-in user), never application permissions.

Source of truth  The redirect URIs and scopes are mirrored from electron/auth/deep-link-loopback.ts, electron/auth/msal-provider.ts, and electron-builder.json5. Keep them in sync with the codebase.

3. Prerequisites

  • Azure CLI (az) on PATH.
  • An account with rights to create app registrations in the {{SCOUT_TENANT_NAME}} tenant (here: {{SCOUT_LICENSED_USER}}).
  • For the bash variant: jq.
  • Sign in to the target tenant first (device code avoids the --username incompatibility):
az login --use-device-code --allow-no-subscriptions
# Complete the code at https://microsoft.com/device as {{SCOUT_LICENSED_USER}}
az account set --subscription "<a-subscription-in-the-{{SCOUT_TENANT_NAME}}-tenant>"
az account show --query "{tenant:tenantId,user:user.name}" -o json
Gotcha  az login --use-device-code cannot be combined with --username ("not applicable with other arguments"). Run device code bare and pick the account in the browser.

11. Troubleshooting

SymptomCause & fix
Scopes show 0 after running update az ad app update --required-resource-accesses silently no-ops on update. The scripts here apply permissions with an explicit az rest PATCH to /applications/{objectId}.
--use-device-code is not applicable with other arguments Drop --username; run device code bare and choose the account in the browser.
AADSTS70016 authorization pending then expiry The device code was not entered in time. Start a fresh az login --use-device-code and enter the new code promptly.
Breadcrumb icon still shows the old/generic logo Entra portal CDN cache. The Branding Logo field is authoritative; the header updates within minutes.
Logo upload rejected Use a square PNG/JPEG under ~256 KB. The helper pads the mascot to 1024x1024 before PUT /applications/{objectId}/logo.
WAM fails on RDP / DevBox / non-AAD-joined Expected - WAM is a Windows-only silent path; MSAL fallback handles it. Not a bug.

12. Additional deployment - rolling to another {{SCOUT_TENANT_NAME}} host

The {{SCOUT_APP_NAME}} registration is tenant-wide. You do not create a new app per machine - every additional {{SCOUT_TENANT_NAME}} node reuses the same public client {{SCOUT_APP_CLIENT_ID}} in tenant {{SCOUT_TENANT_ID}}. A new host only needs (a) the Scout Frontier policy key and (b) an interactive / device-code MSAL sign-in through this registration. The steps below are the manual runbook we follow per host.

Per-host steps

  1. SSH in & identify the box - confirm OS and whether Microsoft Scout / {{SCOUT_APP_NAME}} is installed and its version. 
    ssh <host>        # e.g. ssh framer  ({{SCOUT_TENANT_NAME}} fleet hosts are in ~/.ssh/config)
# Windows:  Get-ItemProperty "HKLM:\SOFTWARE\Policies\Scout" -EA SilentlyContinue
# Linux:    cat /etc/clawpilot/policy.json 2>/dev/null
# macOS:    defaults read /Library/Managed\ Preferences/com.microsoft.clawpilot 2>/dev/null
  2. Set the Frontier policy key (clears the "not set up for your organization" gate). Use the source for the OS:
    PlatformPolicy sourceKey
    WindowsHKLM\SOFTWARE\Policies\ScoutAllowScoutFrontierAccess = 1 (DWORD, PascalCase)
    macOS/Library/Managed Preferences/com.microsoft.clawpilot.plistPascalCase
    Linux/etc/clawpilot/policy.json{ "version":1, "allowScoutFrontierAccess": true } (camelCase)
    No-root fallback<userData>/tenant-policy.jsoncamelCase
  3. Sign in through this registration - public client, no secret. Interactive (deep link) on a desktop session, or device code on a headless box: 
    az login --use-device-code --allow-no-subscriptions
# Complete at https://microsoft.com/device as {{SCOUT_LICENSED_USER}} ({{SCOUT_TENANT_NAME}})
# App/runtime sign-in uses client {{SCOUT_APP_CLIENT_ID}}
# Redirect (Win/Linux): ms-clawpilot://auth/callback
# Delegated scopes: openid profile email offline_access User.Read
#                   Mail.ReadWrite Mail.Send Calendars.ReadWrite Files.ReadWrite Chat.ReadWrite People.Read
  4. Relaunch Scout / {{SCOUT_APP_NAME}} on the host - it reads the policy key at startup (and ~every 15 min). The waitlist screen clears and the account/profile menu should show {{SCOUT_LICENSED_USER}} ({{SCOUT_TENANT_NAME}}).
  5. Verify - see sections 8. Verify and 7. Runbook cards. Confirm the M365 Copilot license is present (satisfies Frontier) and the GitHub Copilot seat is signed in.

Admin consent is already granted tenant-wide (see 10. Admin consent), so no per-user consent prompt is expected. For the broader control-plane wiring (scout-api / scloud-om / sdk / cli) on a node, see the Scout SWE wiki - {{SCOUT_TENANT_NAME}} deployment.
